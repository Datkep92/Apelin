# Tool caps: which ones were needed, which ones were not

2026-11-04. An order asked for a survey of the artificial limits the agent's
tools put on the work, and for the ones that got in the way of honest work to
go, keeping what safety or a protocol needs.

The test used for each one: does it stop the model from doing what it was
asked, or does it only bound one reply?

## Gone

**file_read refused every file over 512 KB.** `ProjectFileTools.maxReadBytes`
was a refusal, not a window: the model got "big.log is 524289 bytes, over the
524288-byte limit" and a hint to shell out, so a large log, a big JSON, a
generated source file were all unreadable by the tool that is meant to read
them. Now the file is read as a window: a file that fits is held whole as
before, a larger one is streamed 64 KB at a time, and each reply shows at most
`maxReadBytes` bytes and `limit` (2000 by default) lines, the note naming the
offset to go on from. Only the lines asked for are kept, so the memory cost is
one piece plus the window and not the file. `readFile`, `readWindow`,
`streamedWindow`, `readAll` and `fill` in
`Packages/ApelinAgent/Sources/ApelinAgent/Tools/ProjectFileTools.swift`.

**A screen capture over 4 MB was dropped.** `ToolRunner.maxImageBytes` is what
a provider takes; over it the picture was thrown away and the model was left
blind to the screen it had been asked to look at, with the byte count as its
only clue. Now the capture is scaled (at most `FileImage.maxPixelSize` px on a
side) and encoded again, and `note` in `CaptureScreenResponse` says what was
shown; under the limit the host's bytes go as they came.

## Kept, and why

- **What a provider or a protocol takes.** `FileImage.maxPixelSize` (1568 px)
  and `maxBytes` (3 MB) — an image a model endpoint will accept, scaled per
  endpoint by `MessageImageLimits`; `HTTPRequest`/`WebFetch` 5 MB a body and 5
  redirects; `ToolRunner.maxImageBytes` 4 MB, the picture inside one reply.
- **What this device will hand over in one go.** `crashRead` 256 KB;
  `AgentSession.maximumAttachmentBytes` 32 MB.
- **What the thing being read may cost.** `FileImage.maxSourcePixels` 64 MP
  before a decode is attempted.
- **The caller's own budget, said out loud rather than silently.** `find`
  20000 entries, `grep` a 2 MB file cap and 300-character excerpts, a diff 400
  lines, `JavaScript` 32 KB of output, skill bodies 64 KB / files 256 KB / a
  100-file list, the browser's controls and matches, `UITreeFilter` 1000
  elements: each of these ends in a reply that says it was cut.
- **The tool's own parameter.** `file_read` 2000 lines, `find` 200 and 2000,
  `listCrashes` 200/20, `file_show` 8 files: the model asks for these.

## Candidates, not changed here

- `grep` reads a file through `try? readText(file, limit: 2 MB)`, so a file it
  cannot read — over 2 MB, or binary — is skipped in silence. It could stream
  the way file_read now does, and say which files it skipped.
- The browser caps (`BrowserTool.maximumControls` 48, `maximumMatches` 20,
  `maximumElementText` 240) and `HTMLText`'s 4096-byte head: item 3 of order
  `0825a253`.
- `AppRelaunch.maximumInfoPlistBytes` (1 MB) and `SkillReader.maxListedFiles`
  (100).
- shell_run and code_run output is bounded in the host (apelind), not here, and
  was not surveyed.

## How far this is verified

There is no Swift compiler on this device. `Scripts/check-accessibility.py`,
`check-stale-strings.py`, `check-format-strings.py` and
`check-shell-deletes.py` pass, and the escapes and braces of every file touched
were checked by hand; the unit tests (`FileReadWindowTests`,
`ScreenCaptureImageTests`) run for the first time in CI.
